# Emulator evidence and target qualification

M6 verifies the controller, bootstrap, released Scale Set SDKs, and synthesized infrastructure against deterministic local fixtures. The merged evidence covers GitHub delivery, direct EC2 and standalone Fargate execution, and combined controller recovery. A live binding remains pending until its exact GitHub credential scope, AWS account and Region, versions, and runtime environment pass the target checks below. This record covers a single-account, single-Region controller on ECS Fargate and Linux runners on direct EC2 or standalone on-demand Fargate. Follow the deployment and recovery procedures in the [operator runbook](operator-runbook.md), record the chosen resources in the [profile binding template](profile-bindings.md), and use the [telemetry checks](operator-telemetry.md) when collecting evidence.

## What passed locally

The integration gate uses pinned MiniStack 1.5.44, loopback AWS endpoints, a stateful TLS/HTTP/2 GitHub simulator, synthetic credentials, and released Scale Set Client and Listener 0.1.0-alpha.1. The Dockerless integration gate uses simulated one-job processes. Separate Linux bootstrap smoke checks exercise process isolation and cleanup in controlled containers. The Fargate smoke also starts the pinned runner listener and worker locally. Live evidence is limited to the recorded upstream GitHub.com repository canary. Its blind same-session ACK retry progressed the tested delivery around transport loss, but a control DELETE of an unused message ID also returned 204. Keep the delivery pending when a replayed 204 is the only evidence of its historical disposition. Withholding the successful session deletion response produced the same 400 class as a never-issued session ID. An attempted reattach returned an incomplete payload rejected by the client. Organization and enterprise recovery, natural token expiry, and cross-process reattachment remain unqualified. Configuration rejects custom GHES hosts and custom root CA/mTLS options in this baseline. [Upstream live qualification](https://github.com/knightfall/scaleset.NET/issues/64) · [Released target parser](https://github.com/knightfall/scaleset.NET/blob/v0.1.0-alpha.1/src/ScaleSet.Client/GitHubTarget.cs) · [Released SDK wire tests](../tests/Knightfall.ScaleSet.Aws.SdkContract.Tests/GitHub/GitHubClientContracts.cs) · [Released SDK boundary](dependency-baseline.md#session-recovery-and-qualification-boundary).

- Preserve the exact scope, set, session GUID, confirmed cursor, pending message ID and phase, durable journal/revision and reservation evidence together. With the same client still open, wait for the prior step and resume the stored phase. A reconstructed `Acknowledging` phase with unknown outcome keeps the lane in recovery. Keep that delivery and its reservations pending while reconciling exact evidence.
- After the previous process is lost, fence the previous owner and use a fresh, authorized client to journal and retire the exact old session. Confirmed success or independently verified evidence for that same session permits an independently authorized replacement. The replacement starts from its own initial statistics with an absent cursor.
- A suppressed request, lost response, 400, 404 or elapsed local time leaves an uncertain retirement pending. Retain the old session and message evidence, stop the affected lane from acquiring or advancing the cursor, and resolve through the recorded exact retirement and acknowledgement process. Preserve uncertain reservations across replacement and reconcile any old delivery against its own session identity. ## Pending target checks

Record each item as passed, failed, or pending with its UTC timestamp, operator, AWS account and Region, GitHub target and credential type, controller and runner image digests or AMI, resolved Launch Template or task-definition revisions, runtime SHA-256 and generation, and a sanitized evidence link. Include the matching profile and operation names where applicable. Keep credential material, handoff plaintext, and authorization headers out of the evidence. Changes to identity, platform, network, trust configuration or immutable artifacts require the affected checks to be repeated.

### Ownership and network placement

- **Controller task move and clock.** Run `preflight clock` in the intended Fargate platform and verify the exact task/cluster, Task Metadata v4 clock status and error bound. Exercise an abrupt move from a real previous controller task. The successor must stay in read-only recovery until `DescribeTasks` confirms that exact ARN in the configured cluster is `STOPPED`, the clock margin passes, and outstanding effects are settled against exact records. Missing, partial or mismatched task evidence remains unresolved. [Fargate Task Metadata v4](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-metadata-endpoint-v4-fargate-response.html).
- **EC2 and Fargate placement.** Verify private subnet routes, effective security groups, no public IP, exact ENI identity and attachment evidence, and reachability to required services from the actual subnets. Check live EC2 placement and capacity error responses for the selected numeric versions. For Fargate, record current applied on-demand vCPU quota and measured use in the selected account and Region, including other profiles, plus available subnet IPs and sufficient reserved margin. Recheck freshness after placement pressure or configuration changes. Unavailable, stale or partial evidence remains unknown and prevents new admission based on that evidence. [ECS service quotas](https://docs.aws.amazon.com/general/latest/gr/ecs-service.html).
- **Event delivery.** Verify real provider-generated EC2 and ECS notifications in the configured account/Region, exact EventBridge rule and SQS permissions, and configured queue encryption and DLQ behaviour. Exercise duplicate and out-of-order delivery. An event wakes exact resource readback. Verified binding and provider state are required to advance the record. EC2 state-change notifications give instance ID and state, so the consumer requires independent identity, ownership and placement evidence. [EC2 state-change notifications](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/monitoring-instance-state-changes.html) · [ECS EventBridge events](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ecs_cwe_events.html).

### Runner and credential boundaries

- **EC2 AMI and IMDSv2.** On the exact AMI and boot configuration, verify IMDSv2 tokens and effective hop limit. From the real unprivileged runner user and a nested rootless-container job, test both `169.254.169.254` and `fd00:ec2::254` against the firewall, verify denial and absence of AWS credentials, and confirm that there is no sudo, capability or privileged-socket path to bypass isolation. Verify the privileged supervisor alone can obtain the exact instance identity and role credentials, and that RAM-backed private scratch, no-swap and cleanup controls withstand a real one-job run. Keep `publishStatus` off until the exact host proof and optional EC2-only IAM grant are verified. [EC2 bootstrap checklist](ec2-runner-bootstrap.md#qualify-the-isolation-boundary-before-enabling-status) · [IMDS options](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-instance-metadata-options.html).
- **Fargate process isolation.** Verify actual Linux architecture, approved image digest and one essential runner container, cgroup v2 and no swap, adequate `/dev/shm` and task-local private scratch, privilege drop and no-new-privileges, and real process termination and cleanup. Test job access to the task credentials endpoint as part of the threat model. Task role credentials are scoped to the task, so verify the IAM isolation boundary independently of child environment sanitization. Verify the leading-key policy independently, with zero Fargate `STATUS#` permissions. [Fargate bootstrap qualification](fargate-runner-bootstrap.md#qualification) · [Fargate task limits](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/fargate-tasks-services.html) · [ECS task IAM roles](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-iam-roles.html).
- **AWS identities and secrets.** In the deployed environment, sample two distinct instance sessions or task sessions per selected backend, including peers with the same role. Confirm that the STS identity matches the caller identity seen by the HELLO broker, using `RoleId:ShortInstanceId` or `RoleId:ShortTaskId`. Verify each role's URL-only HELLO registration and one-time `OFFER#` delete. Confirm denial of direct HELLO table writes, peer or other-table keys, and direct broker invocation. Verify the controller application role can read only the selected GitHub `AWSCURRENT` secrets and intended CMKs on the permitted service path. Verify the separate ECS execution role can inject only the configured OTLP-header secret references and intended CMKs. The dry-run application role and runners have zero Secrets Manager read access. Validate real key policies, encryption context and secret rotation. [Lambda URL permissions](https://docs.aws.amazon.com/lambda/latest/dg/urls-auth.html) · [DynamoDB condition keys](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/specifying-conditions.html) · [Secrets Manager encryption](https://docs.aws.amazon.com/secretsmanager/latest/userguide/security-encryption.html) · [ECS execution-role permissions](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task_execution_IAM_role.html).

### Telemetry and recovery data

- **OTLP receiver and exporter.** Verify target DNS, routing, TLS trust and authentication for the selected protocol and each enabled signal. Confirm independent header injection/rotation, redaction, bounded series and queues, correct profile correlation, sampling and retention. Check sustained-alert and missing-data behaviour. Drop or stall export and verify acknowledgement, lease renewal and recovery continue, then verify resumed export. The local payload checks cover controller emission and fault isolation over HTTP/protobuf and gRPC. Target collector, storage and alerting each need their own evidence. [OTLP integration PR #49](https://github.com/knightfall/scaleset-dotnet-aws/pull/49) · [Operator telemetry](operator-telemetry.md) · [ECS secret injection](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/secrets-envvar-secrets-manager.html).
- **Isolated restore.** Exercise the selected backup or export/import method and its actual data objects, versioning, encryption and recovery window against a separate target. AWS on-demand backups are asynchronous and do not guarantee a causally consistent snapshot at the exact request instant. Fence the prior controller, establish an independent target and deny old runner access to it. Verify target indexes, TTL, point-in-time recovery, key policies and strong paginated purge of all restored `HELLO#`, `OFFER#` and untrusted `STATUS#` rows before reopening bootstrap. Reconcile held launches with exact provider readback and record zero duplicate launches, then re-enable bootstrap against the renewed scope. Preserve source state for audit. [AWS export](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_ExportTableToPointInTime.html) · [AWS backup](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_CreateBackup.html) · [AWS restore](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_RestoreTableFromBackup.html) · [Operator restore and rollback](operator-runbook.md).
