## Release decisions and qualification

- Admission and retirement both require current, authenticated evidence. An empty GitHub poll, an idle flag, a timeout, or absent ECS task metadata cannot independently authorize an acquisition, stop, or takeover. For connected warm runners, an operator-assisted route is acceptable when the target cannot provide an authoritative scheduling fence. Document the exact procedure, residual limits and evidence required for completion.
- Distinguish first dispatch from recovery after a possibly accepted request. Preserve request identity, quota accounting, session ownership and uncertain reservations across retries and process replacement.
- Treat Fargate task credentials as reachable by workflow code when designing IAM. Record the live qualification needed for the init and metadata layouts, cross-account EventBridge delivery, isolated predecessors, and each supported customer-managed key. Default and externally managed encryption require separate coverage.
- Review item 11 also suggested explicit controller capabilities/GID, narrowing a metadata test endpoint and reducing key or buffer lifetime. These are hardening observations. Prioritize a change if the implementation establishes a supported boundary it improves. The reported universal fork-checkout failure, remote-log loss, six-hour broker outage, platform metadata shape and cross-account flooding scenario require evidence. Keep a named disposition for each without presenting it as a reproduced incident.
- Record the source and applicability of each image advisory. The alpha.1 scan and SPDX files remain historical evidence. Review the candidate against the advisory data and actual bytes selected for alpha.2. [Image advisory record](IMAGE-SECURITY.md) · [Publication process](PUBLISHING.md)

## Combined candidate acceptance

1. Use one integration branch and a draft PR against current `main`. Keep the milestone issues open for review, reference each issue in its implementing commits or PR description, and track any evidence-dependent limitation explicitly.
2. Run `make check`, both Linux bootstrap smoke suites, the release-helper tests and the Markdown link checker. Exercise a retained alpha.1 table and config through upgrade and restart. Include at least one mixed deployment with distinct EC2 templates, Fargate task definitions, labels and capacity limits. A fault in one profile must leave healthy peers able to serve work.
3. Verify hosted CI, CodeQL, and both native controller candidate image builds on the final PR head. Record per-architecture OCI archive and manifest hashes, SBOM subject, scan database timestamp and advisory disposition. Distinguish local fixtures, emulation, native hosted evidence and outstanding AWS or GitHub target checks. [Qualification boundaries](../emulator-boundaries.md)
4. Return the PR URL, immutable head SHA, per-issue disposition, checks and evidence links, migration/operator impact, unresolved review threads and any proposed scope exception to the requesting reviewer. A scope exception requires an explicit decision. Wait for approval on that exact SHA before merge. A new head needs review again. Tagging, production approval, release publication and live deployment require separate authorization.
